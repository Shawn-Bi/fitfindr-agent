# Integrating FitFindr

How another agent, app or product can use FitFindr, and what to settle before
merging it into a larger product. Everything here matches the code on branch
`v2` (2026-10-30). If code and this file disagree, the code wins: please fix
this file.

FitFindr offers three ways in:

| Way in | Best for | Needs |
|---|---|---|
| [MCP tool `search_listings`](#1-mcp-tool-search_listings) | Another agent that only needs secondhand listings | Python env of `backend/` |
| [HTTP API](#2-http-api) | A web or mobile product that wants search, styling, closet and saved items | A running FitFindr API + Supabase sign-in |
| [`run_agent()` in Python](#3-run_agent-in-process) | A Python orchestrator that wants the whole agent run (search → style → fit card) | Python env of `backend/` |

All three share the same rules and limits: see
[Shared constraints](#shared-constraints-read-before-you-integrate).

---

## 1. MCP tool `search_listings`

`backend/mcp_server.py` is a FastMCP server (stdio transport, server name
`fitfindr`) with one tool. FitFindr's own agent calls its search through it
(`agent.py` → `mcp_client.call_tool`).

**Input**

| Name | Type | Required | Meaning |
|---|---|---|---|
| `description` | string | yes | Keywords for what the user wants, e.g. `"vintage graphic tee"` |
| `size` | string \| null | no | US size as text, e.g. `"M"`. Case-insensitive; `"M"` matches `"S/M"`. |
| `max_price` | number \| null | no | Maximum price in US dollars, inclusive |

**Output:** a list of [standard listing dicts](#standard-listing-dict), best
match first, at most 10. **An empty list `[]` means nothing matched**; it is
not an error. Kids' items are dropped unless the description asks for kids.

**Start it**

```powershell
cd backend
.venv\Scripts\Activate.ps1
$env:PYTHONUTF8=1; $env:FITFINDR_DATA_MODE='fixtures'   # or 'live', see below
python mcp_server.py          # waits on stdin: that's right
python mcp_client.py          # in another terminal: lists the tools it offers
```

**From an MCP client** (any client that launches stdio servers; adjust paths):

```json
{
  "mcpServers": {
    "fitfindr": {
      "command": "D:/path/to/FitFindr-Agent/backend/.venv/Scripts/python.exe",
      "args": ["mcp_server.py"],
      "cwd": "D:/path/to/FitFindr-Agent/backend",
      "env": { "FITFINDR_DATA_MODE": "fixtures", "PYTHONUTF8": "1" }
    }
  }
}
```

If your client has no `cwd` option, pass the full path to `mcp_server.py` in
`args`. The server reads `.env` from the repo root, so keys never go in this
config.

**From Python**

```python
from mcp_client import call_tool   # run from backend/
results = call_tool("search_listings", {"description": "denim jacket", "size": "M", "max_price": 40})
```

**Data mode matters.** With `FITFINDR_DATA_MODE=fixtures` the tool reads
recorded real responses in `backend/tests/fixtures/` (only a few queries are
recorded, so most searches return `[]`). With `live` it calls the store APIs:
each new query is one counted RapidAPI call per store host, then cached 24 h.
Live mode needs Supabase (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) for the
cache and the monthly counter; if the counter can't be read, the store is
skipped (fails closed).

## 2. HTTP API

FastAPI app in `backend/api/main.py`. Production base URL:
`https://fitfindr-api.onrender.com`. The full schema is generated by FastAPI
at `/docs` (interactive) and `/openapi.json`.

**Auth.** Users sign in with Supabase Auth in the browser. Send the Supabase
access token as `Authorization: Bearer <token>`. The API reads and writes user
data with that token, so row-level security applies: a user can only see
their own closet, saved items and profile. Routes marked "guest OK" also work
without a token.

**CORS.** Only origins in `FRONTEND_ORIGINS` (comma-separated) or matching
`FRONTEND_ORIGIN_REGEX` may call it from a browser. A new frontend needs its
origin added on the API host.

| Method and path | Auth | What it does |
|---|---|---|
| `GET /health` | none | `{"ok": true, "data_mode": "live", "env": "production"}` |
| `GET /stores` | none | Store status bar: one row per store (see below) |
| `POST /search` | guest OK | Search + styling + fit card. `style: false` returns results only (no model calls) |
| `POST /search/style` | guest OK | Styling + fit card for one listing, after a `style: false` search |
| `GET /home` | user | "Picked for your closet" (no live calls) |
| `GET /closet/items` · `POST /closet/items` | user | List / add a closet item (multipart: `data` JSON + `photo`) |
| `GET` · `PATCH` · `DELETE /closet/items/{id}` | user | Read / edit / delete one item |
| `POST /closet/items/{id}/photo` | user | Replace the photo (JPG/PNG/HEIC, ≤ 10 MB; GPS metadata stripped) |
| `GET /closet/items/{id}/matches` | user | Listings on hand that pair with the item |
| `GET` · `POST /closet/items/{id}/outfit` | user | The AI stylist's saved outfit for the item / rebuild it |
| `POST /closet/autotag` | user | Photo → suggested name, category, colours, style tags, season, gender |
| `GET /saved` · `POST /saved` · `DELETE /saved/{source}/{listing_id}` | user | Saved listings |
| `GET` · `PATCH /profile` | user | Sizes, styles, colours, budget, gender, location |
| `DELETE /account` | user | Deletes the account and all its data (hard delete) |
| `GET /dev/traces` | dev only | Latest agent runs; 404 in production |

**`POST /search` body** (only `q` is required):

```json
{
  "q": "vintage graphic tee under $30",
  "style": true,
  "use_profile": true,
  "no_size": false, "no_price": false,
  "max_price": null, "min_price": null,
  "sizes": null,
  "conditions": [], "colors": [], "gender": null,
  "within_days": null, "stores": [], "location": null
}
```

`conditions` items: `new_with_tags | new | like_new | good | fair`.
`gender`: `women | men | any`. `within_days`: `1 | 7 | 30`.
`stores` items: `depop | poshmark | mercari | etsy | ebay | fb_marketplace`.

**Main response fields:** `parsed` (description, size, sizes, max_price,
min_price), `chips` (the conditions shown to the user), `results` (standard
listings plus `saved: bool`), `stores` (status rows), `styling` (`text`,
closet `items` used, or `unavailable` message), `fit_card` (caption),
`fit_verdict`, `clarify` (one question when the request is too vague; no
results then), `empty` (when nothing matched: `title`, `message`, `relax`
options), `relaxed` / `broadened` (what was loosened and why), `agent`
(planner, tool steps, ranking `semantic` or `keyword`).

**Store status row** (`/stores` and `stores` in search):

```json
{"platform": "ebay", "label": "eBay", "status": "paused", "count": 0, "resumes": "2026-11-01"}
```

`status` is `live`, `paused` (monthly stop line reached; `resumes` is set),
`coming_soon` (not connected) or `error`.

**Errors:** `401` sign in again · `422` invalid input (`detail` is a
user-readable sentence) · `429` rate limited, with `Retry-After` seconds ·
`502` Supabase unreachable. Rate limit: 10 full searches a minute per user (per
IP for guests); `style: false` searches get 40.

## 3. `run_agent()` in-process

```python
from agent import run_agent   # run from backend/

session = run_agent(
    "vintage graphic tee under $30",
    wardrobe={"items": [{"id": "c1", "name": "Baggy straight-leg jeans", "category": "bottoms",
                         "colors": ["dark blue"], "style_tags": ["denim", "streetwear"], "notes": None}]},
)
```

Optional arguments: `parsed` (`{"description", "size", "max_price"}` to skip
parsing), `search` (a function with `search_listings`' signature; default is
the MCP tool), `planner` (`"gemini"` default, or `"rules"` with no model
calls for planning), `prefs` (`{"gender": ...}`).

Read the returned session in this order: `session["clarify"]` (a question for
the user), then `session["error"]` (nothing matched, even after relaxing), then
`session["styling_error"]`. Otherwise use `selected_item`,
`outfit_suggestion` (`{"text", "item_ids"}`), `fit_card` and `fit_verdict`.
Every tool step is in `session["steps"]` (tool, arguments, result, ms).

## Data shapes

### Standard listing dict

Every store adapter returns this (`backend/sources/normalize.py`). A value the
store didn't send is `null`, never invented.

| Field | Type | Notes |
|---|---|---|
| `id` | string | Unique within its platform |
| `title` | string | |
| `price` | number | USD |
| `size` | string \| null | US size as the seller wrote it (eBay never sends one) |
| `platform` | string | `depop` · `poshmark` · `mercari` · `etsy` · `ebay` · `fb_marketplace` |
| `url` | string | Link to the original listing page; buying happens there |
| `image_url` | string \| null | The store's own photo |
| `condition` | string \| null | Optional |
| `updated_at` | string \| null | Optional, ISO 8601 |
| `category` | string \| null | Optional, the store's own label (used to drop kids' items) |
| `brand` | string \| null | Optional |
| `listed_at` | string \| null | Optional, ISO 8601 (Poshmark only) |

### Wardrobe dict

```json
{"items": [{"id": "…", "name": "…", "category": "tops", "colors": ["…"], "style_tags": ["…"], "notes": null}]}
```

`category` is one of `tops`, `bottoms`, `outerwear`, `dresses`, `shoes`,
`accessories`. The list may be empty; styling then gives general advice.

### Database (Supabase)

`supabase/schema.sql` + `supabase/migrations/` (apply with
`python backend/scripts/migrate.py`). User tables, row-level security "own
rows": `profiles`, `closet_items`, `saved_items`, `closet_outfits`. Server-only
tables (RLS on, no policies): `api_usage` (monthly call counts), `search_cache`
(24 h raw responses), `traces` (agent runs). Closet photos are in Supabase
Storage, readable only by their owner through signed URLs.

## Shared constraints (read before you integrate)

1. **US only.** US sizes and USD prices.
2. **Never show invented listings.** Every listing must come from a live call
   or a cached real response ≤ 24 h old. Fixtures are for tests only; with
   `APP_ENV=production` and `FITFINDR_DATA_MODE=fixtures` the backend refuses
   to start. Don't fill a paused store with sample data.
3. **Quotas are per RapidAPI host and shared by everything using the same key.**
   Free plan: 50 calls a month per host, FitFindr stops at 40 and resets on the
   1st (UTC calendar month). If several products call FitFindr, or reuse the
   same key, they all draw from the same 40. Repeat searches within 24 h are
   free (cache). `FITFINDR_LIVE_SOURCES` limits which hosts may call live.
4. **Gemini free tier is shared too.** When the model is unavailable, search
   still works, styling says "Styling suggestions are unavailable right now.
   Your search results still work.", and the caption is written in code.
5. **Third-party APIs.** The store data comes from RapidAPI providers, not the
   stores' official APIs. Show the source store and link back to the original
   listing; prices and stock may change there.
6. **Secrets stay in environment variables** (`.env` locally, the host's
   dashboard in production): `GEMINI_API_KEY`, `RAPIDAPI_KEY`,
   `RESALE_API_HOST`, `ETSY_API_HOST`, `FB_MARKETPLACE_HOST`, `SUPABASE_URL`,
   `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_DB_URL`,
   `FITFINDR_DATA_MODE`, `APP_ENV`, `FRONTEND_ORIGINS`, `FRONTEND_ORIGIN_REGEX`.
   The frontend needs `NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` and `NEXT_PUBLIC_API_URL`.

## Checklist for merging into a larger product

- [ ] **Pick the way in.** Agent-to-agent: MCP `search_listings`. Product
      features (closet, saved, styling): HTTP API. One Python orchestrator:
      `run_agent()`.
- [ ] **Accounts.** Share FitFindr's Supabase project (same users, RLS keeps
      data apart), or move the tables into the larger product's project and
      point `SUPABASE_*` at it.
- [ ] **Quota owner.** Decide whose RapidAPI and Gemini keys pay, and whether
      the 40-call stop line is per product or shared. Upgrade to paid plans
      before real traffic.
- [ ] **CORS.** Add the new frontend's origin to `FRONTEND_ORIGINS`.
- [ ] **Tool names.** If the larger product has other MCP servers, keep the
      server name `fitfindr` so `search_listings` doesn't collide.
- [ ] **Keep the contract.** `search_listings`' signature and the listing dict
      are a published contract. Add optional fields; don't rename or remove
      them.
- [ ] **Run the checks** after any change: unit tests and
      `python run_eval.py --label <name>` in fixtures mode (README → Tests).
